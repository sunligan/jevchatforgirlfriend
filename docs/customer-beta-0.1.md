# 客服 Beta 0.1

日期：2026-09-24

## 目标

在现有聊天副驾基础上，先验证“抖音固定话术客服 + 微信线索分发队列”的最小闭环。

## 已实现

### 抖音 Beta 适配

- 包名：`com.ss.android.ugc.aweme` 与 `com.ss.android.ugc.aweme.lite`。
- 使用保守无障碍启发式：当前页面必须有可编辑输入框，并能读到消息区域文字；无法确认时不自动发送。
- 会话标题、最近消息和“我/对方”先转为统一 `ChatSnapshot`。
- 固定回复状态机：
  - 两句都没出现：计划发送第 1 句、第 2 句；
  - 检测到第 1 句已经出现：只计划第 2 句；
  - 两句都出现：不重复回复；
  - 话术为空：提示人工配置，且自动发送不会启动。**两句固定话术的出厂默认值是空的**——之前默认带着两句示例文案，等于操作者还没配置就已经有内容可以发给陌生人了。示例文案现在只显示为输入框提示。

### 自动发送 / 手动确认

- 设置中有“固定话术自动发送”开关，默认关闭。
- 关闭：显示每句固定话术，可分别复制或填入；发送由人确认。
- 开启：只对固定话术逐句填入，并尝试点击可明确识别的“发送”按钮。
- 找不到唯一发送按钮、识别到多个发送按钮或会话状态不确定：停止自动发送，只保留已填入内容并提示人工处理。
- 不使用模型自由生成内容自动发送。

### 联系方式线索

- 识别手机号、微信号，以及“微信 / vx / wx / weixin / 联系方式 / 电话”等暗示。
- **微信号必须同时满足两个条件**：同一条消息里出现联系方式暗示，且候选词本身像 ID（含数字、`_` 或 `-`）。只看形状会把任何 6 个字母以上的英文单词（`please`、`because`）当成微信号，产生幻影线索并响铃。
- 具体手机号/微信号：保存到 App 私有目录 `filesDir/customer/leads.json`。
- 仅有暗示、没有具体号码：不发送任何规避话术，发提示音并提示人工处理。
- 扫描范围是**本轮新出现的对方消息**（最多回看 10 条），不是只看最后一条——客户先发号码再说“在吗”时号码不会漏。同一会话里已扫过的消息不会重复入库。
- 每条线索附带：来源会话、分类、目标微信群、原始文本、创建时间、是否已处理。
- 线索文件可以在「客服线索 / 微信分发队列」页或设置里的「清空知识库、历史与客服线索」一键删除。这是全项目唯一存放**他人**手机号/微信号的文件，必须可删。

### 微信分发队列

- 设置里配置默认分类和默认目标群。
- 线索页面展示待处理记录。
- 一键复制整理好的分发文本，用户打开目标微信群后粘贴并确认发送。
- Beta 0.1 不在未知微信版本上自动点击群聊发送；防止同名群、错群和窗口切换导致误发。

## 当前边界

- 本版不是“遍历整个抖音会话列表并持续无人值守”的最终版本，先以当前打开会话验证闭环。
- 抖音不同版本节点结构差异较大，实际适配必须在目标手机和目标版本上验证。
- 线索分类目前来自设置中的一个默认分类；后续可以做多分类映射和群映射表。
- 微信分发先队列/复制/填入，最终发送由人工确认。
- 自动发送开关只对固定话术生效；模型判断/生成结果不会绕过人工确认自动发送。

## 测试重点

1. 关闭自动发送：抖音当前会话收到新消息后，面板出现固定话术，每句可单独填入。
2. 开启自动发送：只配置测试话术，确认两句按顺序发送；若第一句已在会话里出现，只发送第二句。
3. 给出手机号、微信号、或“加微信”暗示，检查提示音和线索队列。
4. 打开“客服线索 / 微信分发队列”，复制分发文本到测试微信群，手动发送并标记已处理。
5. 切换到普通微信聊天：客服 Beta 不应接管普通微信模型副驾流程。
6. 关闭客服 Beta：原来的个人聊天副驾逻辑继续工作。
7. 不配置任何话术就打开自动发送：面板应提示人工配置，且不发出任何内容。
8. 线索页/设置里的清空按钮：删掉 `leads.json` 后重新进入应为空列表。

## 修订（2026-09-24 下午）

首轮实现（提交 `c7bfdef`）之后的一轮修复，行为变化都已同步到上文：

| 问题 | 修复 |
|---|---|
| `customerLeads.append` 在主线程做 JSON 读写。调用链是主线程防抖 → `maybeCapture` → `handleCustomerSnapshot`，无障碍服务卡主线程会被系统判定无响应并断连 | 移到 worker 线程（`storeLeads`），提示音和 toast 回主线程；同文件的 `KbStore` 调用本来就是包在 `submit {}` 里的 |
| 两句固定话术默认值非空，`needsHuman` 分支永远进不去 | 默认值改成空字符串，示例文案降级为输入框 hint |
| `leads.json` 是全项目唯一存他人手机号/微信号的文件，却没有任何删除入口（「清空知识库与历史」只删 `filesDir/kb`） | `CustomerLeadStore.clear()`；线索页加「清空全部线索」按钮；设置里的清空对话框一并覆盖线索 |
| 每条线索 new 一个 `ToneGenerator` 且不 release，泄漏 native 音频资源 | 服务内单例，`onDestroy` 释放，服务已销毁后不再重建 |
| 微信号正则匹配任意 6–20 字母词，`falsePositives` 只硬排了 6 个词；`please help me` 会变成一条线索并响铃 | 要求「同一条消息有联系方式暗示」+「候选词含数字/`_`/`-`」双条件 |
| 只扫最后一条对方消息，客户先发号码再说别的就漏了 | 增量扫描本轮新出现的对方消息，最多回看 10 条 |
| 自动发送排程逻辑在「立即执行」回调和自动路径里逐字重复两份，`900L` 是无注释魔数 | 合并成 `scheduleAutoSend`，间隔抽成 `CustomerSendSchedule.INTERVAL_MS` 并说明它要覆盖 `fillInput` 最坏 450ms 验证链 |
| 客服会话状态、线索判定、通知文案混在 849 行的 `ChatCaptureService` 里，无法脱离 Android 测试 | 抽出 `core/CustomerSessionController`（纯 Kotlin）：吃 `ChatSnapshot` + `CustomerConfig`，吐 `CustomerAction`；服务只负责执行 |

`isWeChatHint` 之前只有测试在调，生产路径用的是 `phone != null || wechat != null` 的反面，两者不等价；现在通知文案由控制器的 `concrete`/`hinted` 计数决定，语义与它一致。

**已知取舍**：暗示词表里有裸「微信」，所以客户说「我微信上问过了」这类没有留号码的消息也会进队列并响铃。这是文档里「仅有暗示 → 提示人工处理」的既定行为，宁可多提示不要漏号码；如果实际太吵，收窄成「加微信/留个微信/微信号」即可。
